# ADR-0005 — The REQ-001 quality thresholds: still placeholders, and how they get replaced

**Status** proposed — pending measurement · **Date** 2026-08-22 · **Decider** PawChain ID architect

## Context

REQ-001 rejects an aligned crop with Laplacian variance below **120**. That number was
written in Week 1, before a single photograph existed, so every field on REQ-001 could be
filled in — it is a placeholder wearing the costume of a decision. Laplacian variance is
not in any physical unit: it scales with crop size, camera resolution, fur texture and
phone-side sharpening, so "120" means nothing until it is measured against real photos
taken with the real capture protocol.

The same is true for the two thresholds the quality gate added this week alongside blur:
`POSE_RESIDUAL_MAX` (how far the aligned landmarks may sit from the canonical template) and
`ILLUMINATION_CLIP_MAX` (what fraction of pixels may be clipped to black or white). All
three live as named constants in `ml/capture/quality.py`.

## Options considered

1. **Ship a guessed number and call it decided.** Rejected — this is exactly the failure
   Week 1 described and Week 2 exists to fix. A threshold with no sweep behind it is not a
   decision, it is a default someone else picked, dressed up as intentional.
2. **Leave `evals/golden/capture/` empty and defer the whole exercise.** Rejected as the
   final state, but it is the honest *current* state: the golden-set homework (label 150
   crops by eye, across `evals/golden/capture/manifest.json`) has not happened yet, because
   no photographs have been captured yet. `make eval-capture` says so explicitly
   (`status: "golden_set_empty"`) rather than reporting a number nothing measured.
3. **Run the sweep the moment labelled data exists, and amend this ADR in the same pull
   request as the measurement.** This is the decision.

## Decision

Option 3. The procedure that will replace each placeholder, already implemented and
waiting for data (`evals/golden_capture.py::sweep_thresholds`, wired into
`make eval-capture`):

1. Label 150 of the household's own aligned crops by eye: usable / not usable, with a
   reason for every unusable one.
2. Compute blur, pose residual and illumination clip fraction for every one of those 150.
3. Sweep each signal's threshold independently across its full observed range. For every
   candidate cutoff, count what fraction of the "not usable" pile it would still admit, and
   what fraction of the "usable" pile it would wrongly reject.
4. Choose the cutoff for each signal, biased toward rejecting rather than admitting — a
   false reject costs a household a few seconds and a re-capture inside the REQ-012 budget;
   a false admit becomes a permanent, silently weaker stored template (see the trade-off in
   `specs/00-system-spec.md` §5, one layer down).
5. Replace the constant in `ml/capture/quality.py`, replace the number in REQ-001, and
   amend this ADR's `Status` line to `accepted`, in the same commit as the sweep table.

## Because

A specification that only ever answers to itself is not a specification, it is an opinion
with a version number. The sweep is what turns 120 from a guess into a number that answers
to evidence — and the moment that evidence exists, changing the number is not walking back
a decision, it is the decision arriving late for a reason everyone can see in the diff.

## Consequences

- `make eval-capture` exits non-zero today, honestly, with `status: "golden_set_empty"` in
  `evals/out/capture.json` rather than a number. This is not a regression from Week 1's
  `not_implemented` state — it is a stricter, more specific failure: the suite is fully
  implemented and tested against synthetic fixtures (`ml/capture/test_quality.py`,
  `evals/test_golden_capture.py`); only the real-world evidence is missing.
- REQ-001's stated number stays 120 in `specs/00-system-spec.md` until this ADR's status
  changes, and the spec entry keeps saying so.
- `POSE_RESIDUAL_MAX` and `ILLUMINATION_CLIP_MAX` are provisional in the same way and are
  swept by the same procedure once landmark-labelled crops exist (see `specs/open-questions.md`
  OQ-012); they are not yet named as their own REQ, which is itself an open question
  (OQ-013).
