# ADR-0006 — Where golden capture imagery lives, given REQ-009

**Status** accepted · **Date** 2026-08-22 · **Decider** PawChain ID architect

## Context

`evals/golden/` is committed to git and is the frozen answer key every future threshold is
measured against (`evals/golden/README.md`). Raw pet imagery is never committed to the
repository — a house rule in `CLAUDE.md`, and the leading edge of REQ-009 (raw frames are
not retained past 24h in the deployed system; here, they are not retained by git at all).
Those two facts collide unless the golden set's *labels* and its *pixels* are stored
separately.

## Options considered

1. **Commit the images.** Fastest to wire up, and a permanent violation of the house rule
   and of REQ-009's spirit — a leaked git history is a leaked set of pets' faces forever,
   in a way a leaked password is not.
2. **Git LFS inside this repository.** Keeps everything in one place, but LFS storage still
   means the images live in a location this public, MIT-licensed repository controls, and
   still commits raw pet imagery to a history that cannot be un-published.
3. **Reference images by content hash; store the pixels outside git, in a local, gitignored
   directory today and a private pilot store later.** The manifest — paths, SHA-256 hashes,
   labels, and optional ground-truth landmark points — is the only part that is git-tracked.

## Decision

Option 3.

- `evals/golden/capture/manifest.json` is git-tracked: one entry per labelled crop, with a
  stable `id`, a `relative_path`, a `sha256`, a `label` (`usable` / `not_usable`), a
  `reason` when not usable, and an optional `landmarks` block (see task-201).
- The pixels the manifest references live under `PAWCHAIN_GOLDEN_IMAGES`, an environment
  variable defaulting to `data/golden/capture/` — already covered by the `data/` line in
  `.gitignore`.
- `evals/golden_capture.py::verify_hashes` recomputes the SHA-256 of every referenced file
  and fails loudly on any mismatch, so a manifest cannot silently drift from the pixels it
  claims to describe.
- A later week (pilot scale) replaces the local directory with a private object store
  behind the same environment variable; the manifest format does not change.

## Because

The manifest is metadata — filenames, hashes, human judgments — none of which is a pet's
face. It can be reviewed in a pull request diff exactly like any other spec change. The
pixels stay wherever the operator's own device already has them, exactly like the Week 1
homework's `data/capture_log.csv` pattern, and never enter git history to begin with —
which is a stronger guarantee than "retained ≤ 24h" (REQ-009): retained zero hours, by
construction.

## Consequences

- `evals/run.py --suite capture` requires `PAWCHAIN_GOLDEN_IMAGES` (or the default
  `data/golden/capture/`) to exist locally before it can compute anything past
  `status: "golden_set_empty"`. CI does not have this directory and is not expected to —
  the capture suite's real numbers are produced locally, on the operator's own machine,
  against the operator's own cats, and the resulting `evals/out/capture.json` is what gets
  reported in the pull request description, not regenerated by CI.
- Two people working on this repository will have different local pixels behind the same
  manifest unless they explicitly share the `data/golden/capture/` folder out of band. That
  is an accepted cost of never letting pet imagery enter git.
- If `PAWCHAIN_GOLDEN_IMAGES` points at a shared network location later, `verify_hashes`
  becomes the only thing standing between "the manifest says usable" and "someone quietly
  replaced the file."
