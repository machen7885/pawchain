# ADR-0002 — Why a chain at all, and which one

**Status** accepted, with a stated revisit trigger · **Date** 2026-08-15 · **Decider** PawChain ID architect

## Context

"Why does this need a blockchain?" is the strongest question anyone asks about this
project, and it deserves a straight answer rather than a defensive one. Most projects that
add a chain do so for reasons that a database satisfies more cheaply. If the chain cannot
be defended here, the correct engineering answer is to drop it — a project that removed
its blockchain for a written reason is more credible than one that kept it for none.

The deployment context is mainland China: public-chain token trading and stablecoin
payments are not lawful, which removes the usual justifications entirely.

## Options considered

1. **Signed append-only log in PostgreSQL, no chain.** Cheap, fast, easy to operate, and
   entirely sufficient — as long as every participant trusts the registry that runs the
   database not to rewrite it.
2. **Permissioned consortium chain** (FISCO BCOS / BSN-style) with the registry, vet
   associations and shelter partners as nodes, and fiat/e-CNY-denominated escrow at the
   application layer.
3. **Public chain with an on-chain token.** Not lawful in the deployment context. Rejected
   without further analysis.

## Decision

Option 2, for the attestation and PetID record. The money leg is application-layer
fiat/e-CNY escrow, not an on-chain asset.

## Because

The narrow, defensible case is this: **multiple parties who do not fully trust each other
— households, vets, shelters, and the registry itself — need a tamper-evident record of
who attested what, and when, that no single one of them can quietly rewrite.** A household
whose deposit is about to be slashed has to be able to check that the vet attestation
record was not edited after the fact by the same organisation running the adjudication.
That is a real property, it is exactly what a consortium chain provides, and Option 1 does
not provide it while the registry holds the write key.

Everything beyond that property is decoration. We are not claiming decentralisation,
censorship resistance, or a financial system. We are claiming a multi-party record with no
single editor.

## Consequences

- Weeks 6–7 carry consortium-chain operational cost: node setup, key management, an
  indexer, and a devnet that has to run in CI.
- The money leg never touches the chain, so "escrow" is a contract state machine plus an
  off-chain payment reconciliation, with all the failure modes that implies.
- We accept slower writes and a harder local development story than a database would give.

## Revisit trigger

If, by the end of Week 7, the consortium chain has exactly one node operated by us, then
the trust property above is not actually present, and this ADR is superseded by one that
adopts Option 1. Multi-party is the entire justification; a single-operator chain is a
slow database with a worse story.
