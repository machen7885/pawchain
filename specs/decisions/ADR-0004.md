# ADR-0004 — Week 2 dependencies: numpy, Pillow, torch, ONNX Runtime

**Status** accepted · **Date** 2026-08-22 · **Decider** PawChain ID architect

## Context

`ml/` shipped Week 1 with zero pip dependencies — there was no application code, so there
was nothing to depend on. Week 2 adds a real capture pipeline (detect, select, landmark,
align, quality-gate) and its eval harness, which need array math, image decoding, and a
path to an on-device model format. `CLAUDE.md` requires a decision record before any new
dependency lands.

## Options considered

1. **Stay dependency-free** — implement image decoding and array math by hand. Rejected:
   decoding JPEG/PNG from scratch is not a reasonable use of the time budget, and numpy is
   already implied by the pinned stack's "PyTorch 2.x, ONNX Runtime" line.
2. **Add only what Week 2 strictly needs, each with a stated job** — numpy for array math,
   Pillow for image decoding, torch for the export path, onnx + onnxruntime to validate and
   run exported artefacts. This is the option below.
3. **Add a full CV framework (OpenCV)** — rejected for now. It pulls in a large, partially
   overlapping surface (its own image I/O, its own array type) for capability numpy +
   Pillow already cover this week. Revisit if a later week needs video capture or camera
   calibration.

## Decision

Option 2. Four dependencies, each doing one job:

| Package | Job | Where it is used |
|---|---|---|
| `numpy` | Array math: the affine solve, the warp, the Laplacian, the illumination stats | `ml/capture/*.py` |
| `Pillow` | Decode JPEG/PNG frames into arrays | `evals/golden_capture.py` |
| `torch` | Already pinned (`CLAUDE.md` Stack). Used this week only by the ONNX export utility, imported lazily | `ml/capture/export.py` |
| `onnx`, `onnxruntime` | Validate an exported graph and run it for latency benchmarking | `ml/capture/export.py` |

## Because

Each package maps to exactly one job description above; none is added speculatively.
`torch` and `onnxruntime` were already named in the pinned stack in Week 1 — this is the
first week code actually imports them, not a new decision to add them. HEIC decoding
(the default format on iPhone) is explicitly **not** handled: the golden-set README asks
for JPEG or PNG exports, and a HEIC-to-JPEG conversion step stays a manual pre-processing
note rather than another dependency.

## Consequences

- `pyproject.toml` gets a real `[project.dependencies]` list for the first time.
- CI (`.github/workflows/gates.yml`) now installs `numpy`, `Pillow`, `torch` (CPU wheel),
  `onnx` and `onnxruntime` before `make gate`. The `torch` CPU wheel is the largest single
  addition to CI time this project has made; accepted because the alternative is an
  untested export path.
- `ml/capture/export.py` imports `torch`/`onnx`/`onnxruntime` lazily, inside the functions
  that need them, not at module load — so `capture.process()` and the quality gate, which
  run on every frame, never pay for an import they do not use.
- No detector or landmark model is trained this week (see `specs/open-questions.md` OQ-011).
  These dependencies land now so the export and benchmarking path is built and tested
  before there is a model to run through it — matching the harness's own rule
  (`specs/tasks/README.md`): build the gate before the thing it gates.
- `ml/capture/export.py::export_onnx` calls `torch.onnx.export(..., dynamo=False)` — the
  legacy TorchScript-based exporter, not torch 2.9's new default (`dynamo=True`), which
  needs an additional `onnxscript` dependency this task does not otherwise require. Torch
  logs a deprecation warning for this choice; accepted for now, revisit when a real model
  exists to export and the dynamo path's feature set actually matters.
